# 5.16.0

Fixes increment delivery plans that could never be saved, and lets callers tell a rejected plan from a temporary conflict.

## Plan names fit the platform's limit

`HierarchicalProjectDelivery.PrepareIncrementAsync` named a new plan `"Increment: "` followed by every selected epic title, with no length limit. The platform rejects plan names longer than 160 characters, and the name was rebuilt the same way on every retry, so the plan was never saved and the sprint never started. On 2026-11-10 a single agent-written epic title produced a 204-character name.

The name now fits. If all epic titles fit, they are all listed as before. Otherwise the name keeps the first epic title, shortened with an ellipsis if needed, and adds the number of other epics, for example `Increment: Core loop (+3 more)`. The plan's epics are still identified by `EpicItemIds`; the name is only for people. Existing draft names are reused unchanged. A retry after this fix reuses the workflow tickets that earlier attempts created, because tickets are replayed by idempotency key.

## `DeliveryStaffingException.RejectedByPlatform`

New, additive. `true` when the platform rejected the delivery plan configuration itself (`work.delivery.configure.v1`), so repeating the same request cannot succeed. Callers should escalate instead of retrying on a timer. The platform now marks a revision race as retryable; platforms released before that report every conflict as non-retryable, so on those a race can also show up as a rejection.

No manifest or protocol change. Works with existing platforms.

Validation: not yet run. Run the SDK, sample and generated-template tests before publishing. New tests: `DeliveryPlanNameTests`.
